# Security

## Identities

| Who | Proves it with | Accepted on |
|---|---|---|
| User (browser) | identity from the auth proxy: trusted header from `trusted_proxies`, or a JWT assertion verified against a JWKS; `dev_identity` for local development | `/`, `/launch`, `/api/v1/environments`, `/api/v1/launch-tickets` |
| Client (editor on a device) | access token (15 min) and rotating refresh token (12 h) from a ticket | `/api/v1/sessions*` |
| Editor connection | stream token (60 s) bound to one session | `/data/v1/stream` |
| Agent | per-env agent token; only its SHA-256 is in `server.toml` | `/agent/v1/connect` |
| REH | connection token, generated by the agent, sent only in the session response | inside the stream, checked by the REH itself |

Grants are checked when a ticket is created, when it is redeemed, on every session request
and on every stream. Removing a grant from `server.toml` takes effect on the next request
after a restart.

## Secrets

- All tokens are 32 random bytes. The server stores only SHA-256 hashes, in memory or in
  `state_file` (mode 0600, written atomically).
- No credential is ever put in a URL except the launch ticket, which is single use, valid
  for 60 s and bound to user, env and project.
- The client keeps tokens in VSCodium's `SecretStorage`.
- The REH listens on 127.0.0.1 only, with `--connection-token-file` (mode 0600).

## Proxy setup rules

- Strip the identity header from client requests in the proxy (see `deploy/examples/nginx.conf`).
- Keep `trusted_proxies` as narrow as possible. The header is ignored from anywhere else.
- `/api/v1/tokens*`, `/api/v1/sessions*`, `/data/*`, `/agent/*` must bypass the proxy login;
  they don't trust any identity header.
- With `[auth.jwt]`, only asymmetric algorithms are accepted, and audience, expiry and
  (optionally) issuer are checked. Unknown key ids trigger a rate-limited JWKS refresh.

## Public client download

`/downloads/remotium-client.vsix` (+ `.sha256`), `/install.sh` and `/install.ps1` need no
login: they only hand out the client package that ships with the server. The scripts carry
the package's SHA-256 and refuse to install a file that doesn't match it. Piping a script
into a shell trusts the server and its TLS certificate; users who prefer can download the
VSIX and check the hash themselves.

## Browser-facing endpoints

`POST /launch` and `POST /api/v1/launch-tickets` reject requests with
`Sec-Fetch-Site: cross-site` or a foreign `Origin`. The dashboard sets `Cache-Control: no-store`.

## Client-side checks

The one-time setup only ever adds `remotium.client` to `enable-proposed-api` in VSCodium's own
`argv.json`, after the user confirms.

The extension asks before using a server the first time (unless it equals the configured
`remotium.serverUrl`) and warns about plain HTTP to non-loopback hosts. A link pointing
at an unknown server can therefore not silently connect the editor somewhere else.

## REH downloads

The agent only downloads from `AGENT_REH_URL_TEMPLATE`. It requires a matching
`.sha256` file unless `AGENT_ALLOW_UNVERIFIED_DOWNLOADS` is set, checks that the extracted
`product.json` has the requested commit, and validates version fields before they reach a
path or URL. Extraction uses the `tar` crate's path-traversal checks.

## `dev_identity`

It signs in every request from `dev_identity_from` (default: loopback) as one user, and the
server logs a warning at startup. The compose file widens it to private networks because
Docker's port forwarding doesn't preserve the loopback source. Never use it on a public machine.

## Not covered yet

- Rate limiting of the token endpoints (put it in the proxy for now).
- Per-user isolation inside one environment: everyone granted an env gets the same Unix user.
- Native OIDC in the server (planned, Phase 4).
